范围：分析原因、提出优化方案并验证关键假设。本轮不实施页面优化、不替换公开媒体、不发布；试编码只在内存生成。验收依据为实际资源大小、代码加载策略、MP4 索引位置、线上响应及可复核的改进方案。技术诊断不等于用户验收。

## Home：原图直接传输，没有响应式衍生图

`src/pages/index.astro` 直接通过 img 引用 `public/images/winet-lab-wordcloud.png`，无 srcset/sizes。原图 2154×1614、1,854,233 字节（1.85 MB / 1.77 MiB）。桌面布局图片最大约572.5 CSS px，手机也请求同一原图；高清屏需要按设备像素比选图，不能简单只按 CSS 宽度导出。

现有 eager、fetchpriority=high、decoding=async 及宽高已配置；主因不是缺少加载优先级。public 中的普通静态图片没有经过 Astro 图片处理。系统字体和内联 SVG 标识不引入外部字体/标识图片请求。

用项目已安装的 Sharp 对同一原图进行内存试编码，保持比例、不裁剪：

| 宽度 | WebP 无损编码字节 | WebP quality=85 字节 |
| --- | ---: | ---: |
| 640 | 175,560 | 42,976 |
| 1120 | 406,226 | 89,560 |
| 1600 | 689,152 | 129,230 |
| 2154（原尺寸） | 1,020,072 | 168,670 |

只有原尺寸无损方案保持原图像素尺寸；其余方案的缩放本身会改变细节。1120px 无损编码版本比原 PNG 小约78%，原尺寸无损小约45%；这些是文件体积结果，不是已测得的加载时间提升。尚未进行各尺寸小字/彩色边缘目视验收，不能认定 quality=85 或最小版本清晰度已通过。

建议：用 Astro 构建时图片管线（导入 src 中的图源）或统一构建脚本生成 WebP 与 PNG 回退，配合 srcset/sizes，让浏览器按布局与像素比选图。保留原图、比例、内容及首图高优先级。优先比较无损 WebP 和适量有损版本，词云小字清晰度优先；不把首页主图改成通用懒加载。生成多尺寸要自动化，避免日后维护者手动管理每种尺寸。

## Research：码率、同时加载与索引位置叠加

本轮重新读取5个 preview.mp4 的文件长度，使用已有 FFmpeg 7.1 只读读取元数据，并通过 Node 逐个解析 MP4 顶层 box：

| 预览 | 大小 MiB | 时长 秒 | 分辨率 | 总码率 Mbps | moov 索引 |
| --- | ---: | ---: | --- | ---: | --- |
| 机械超表面 | 73.85 | 78.67 | 1920×1080 | 7.874 | 文件末尾，offset 77,383,369 |
| EEG | 30.42 | 34.09 | 968×544 | 7.484 | 文件末尾，offset 31,859,710 |
| 磁场/RF计算 | 19.50 | 41.47 | 1920×1080 | 3.944 | 前置 |
| Mighty | 8.83 | 102.33 | 1280×720 | 0.723 | 前置 |
| 心脏监测 | 6.22 | 35.09 | 1280×720 | 1.488 | 前置 |

五段合计138.81 MiB，均为 H.264，已有封面约49–67 KB。文件总量不是首屏实际下载量。Demo ZIP/PDF为普通下载链接，没有代码主动预加载它们，不能把这些文件大小计入首屏媒体流量。

`src/components/ResearchPaperCard.astro` 为所有视频直接设置 src/autoplay/loop/muted/playsinline，preload=metadata 不保证仅取元数据，实际自动播放与缓冲受浏览器策略影响。尚无视口加载和离屏暂停逻辑，存在多视频争用带宽/解码资源的风险；本轮未记录真实浏览器瀑布图，不能断言每次五段均同时完整下载。

大文件不必完整下载才能播放，但高码率提高持续播放所需吞吐。两段尾部索引需额外获取末尾信息，弱网和高延迟下可能加重起播等待。即使不重编码，faststart也可前移索引；它主要改善起播读取顺序，不会大幅压缩文件。

建议：

1. 为卡片生成独立预览副本，最高约720p、不放大小尺寸原片，H.264/兼容像素格式并添加 faststart。先处理机械超表面、EEG和磁场/RF；通过清晰度与实测码率决定参数，Mighty已有低码率，不应机械地强压全部视频。保留时长及现有可开启音轨，缩短片段或去音轨需另行讨论。
2. 在公共组件实现一次共享 IntersectionObserver：临近视口才赋予媒体 src并加载，可见时静音自动循环，离屏暂停，回到页面后按状态恢复；保留原生控件，尊重访客手动暂停，处理自动播放被拒绝和无脚本回退。单纯修改preload无法可靠限制请求；暂停已经加载的视频也不保证立即停止所有缓冲。
3. 继续用封面显示等待状态。当前超表面和Mighty的 preview/demo 共用文件路径，压缩前必须先拆分，保证完整Demo仍可下载原质量文件；以哈希校验原始下载字节。
4. 暂不引入自适应流媒体、外部播放器或新托管。优化后若跨地区实测仍明显受网络限制，再单独评估对象存储/CDN的访问表现、费用和维护方式。

本轮不是用户网络或多地区性能测试，没有测速吞吐、LCP或真实首帧延迟基线。GitHub Pages访问链路可能是影响因素，但不能凭当前资料将慢全部归因于平台，或承诺更换CDN一定改善。

## 建议实施顺序与验收

建议首个实现子任务仅处理Home：生成候选图，核对320/390/768/1440px及高清屏的小字清晰度、完整比例和布局，比较冷缓存请求字节与图片显示/LCP。用户确认后再进入Research子任务。

Research验收：在相同设备、网络限速、视口和冷缓存条件下多次对比，记录首帧时间、卡顿和前10秒媒体传输量；远离视口的视频不发起MP4请求，可见视频无需点击即可循环，滚动后正常加载，手动暂停不被擅自覆盖。检查moov前置、手机/桌面清晰度、根路径与/WiNet-Lab/路径、原Demo哈希一致及受限PDF仍不可访问。随后由用户确认是否发布；本轮分析请求不自动产生新上传授权。
